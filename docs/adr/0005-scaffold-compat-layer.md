# 0005. Слой совместимости с каркасом и граница провайдера модели

## Контекст

Автопроверка Хекслета прогоняет отдельный набор тестов, который опирается на раскладку модулей из шага «Каркас». Имена директорий, модулей и функций оттуда соблюдаются буквально. Живой модели в этом наборе нет: обращения к ней подменяются патчами.

Рабочая реализация выросла вокруг других границ: таблица `fragments`, активности Temporal и `LlmClient` на `httpx`. Часть имён из каркаса поэтому осталась тонким слоем над настоящим кодом. Читателю нужно знать, какой слой настоящий.

## Решение

### Боевой поток

```
POST /documents      → DocumentWorkflow → services/ingest → repositories/documents (fragments)
                                        → services/index  → repositories/search (embedding)
POST /generate-card  → CardWorkflow → services/retrieve → services/security (PII, инъекции)
                                    → services/pipeline → LlmClient
                                    → проверка ссылок → filter_card_output → ожидание сигнала
```

Правила (маскирование, отсев инъекций, проверка ссылок, пороги) определены здесь.

### Слой совместимости

В боевом потоке он не участвует, но и отдельной жизнью не живёт: он идёт через те же модули и правила, что основной поток (раздел «Что общего у двух потоков»).

| Что | Где | Чем является |
|-----|-----|--------------|
| Поиск, эмбеддинги, индексация | `app/rag/retrieval.py`, `embedder.py`, `reindex.py` | реэкспорт `services/retrieve`, `embeddings`, `index` |
| Сборка контекста | `app/rag/context.py` | то же для `FragmentHit`, плюс форма по словарям чанков |
| PII и инъекции | `app/guardrails/pii.py`, `injection.py` | реэкспорт `services/pii`, `injection` |
| Защита контекста и выхода | `app/guardrails/__init__.py` | `guard_context`, `guard_output` поверх `screen_hits` и `filter_card_output` |
| Сквозной RAG по чанкам | `services/rag_pipeline.py`, `services/structured.py` | `retrieve_context_async` читает тексты из `chunks` (`load_chunks`), пропускает их через `guard_context` и только потом собирает контекст. `run_rag_pipeline` проверяет ссылки по базе и пропускает карточку через `guard_output` |
| Поиск по `chunks` | `repositories/chunks.py`, таблица `chunks` (миграция `0006`) | psycopg, формат чанков каркаса |
| Вызов агента | `llm/client.py`: `Runner`, `setup_llm`, `run_agent`; `services/pipeline.py`: async `extract`, `run_pipeline` | `Runner.run` вызывает `LlmClient`: берёт у агента `instructions`, `schema` и `cheap`. Остальное — точки для патчей в тестах |
| Синхронное соединение | `core/db.py`: `with connection()` | psycopg. Перед работой применяет недостающие миграции (`apply_migrations_sync`; при `AUTO_MIGRATE=false` только проверяет их), своих таблиц не создаёт |
| Имена настроек | `Settings.embed_dim`, `Settings.suspicious_chunk_limit`, `setup_logging` | алиасы |

Боевой поток в таблицу `chunks` не пишет. Схему определяют только миграции из `db/migrations` (см. [0002](0002-sql-migrations.md)). Асинхронный `async with connection()` берёт соединение из пула, это основной путь.

### Что общего у двух потоков

- **Схема.** Одна, из миграций. Синхронный `with connection()` и `python -m app.core.migrate` применяют одни и те же файлы под одной advisory-блокировкой, поэтому порядок запуска не важен. Для вставок в форме каркаса (`INSERT INTO documents (id, kind)`) миграция `0007` задаёт умолчания, а `0008` ограничивает их строками с `kind`: строка без `kind` (рабочий поток) обязана задать имя файла, статус и путь. `content_hash` остаётся уникальным, умолчание каждый раз новое.
- **Защита.** Маскирование PII и двухуровневый детектор инъекций (правила, затем дешёвая модель; модель недоступна — фрагмент подозрительный). Подозрительные фрагменты исключаются всегда, порог на это не влияет.
- **Порог блокировки документа.** Одно правило, `Settings.too_many_suspicious`: документ закрыт, если подозрительных фрагментов строго больше `suspicious_chunk_limit` (он равен `INJECTION_BLOCK_THRESHOLD`, по умолчанию 2). Его вызывают `screen_hits`, `guard_context` и `SecurityReport.needs_review`. Согласованность проверяет `test_all_blocking_places_use_one_threshold`.
- **Вызовы модели.** Один путь, `LlmClient`: таймаут, повторы, учёт в `llm_calls`, дешёвая модель для критика и детектора.

### Осознанные отличия

Часть отличий делает слой совместимости слабее боевого потока. Они названы ниже прямо, как ослабления.

- **Порог блокировки документа (ослабление).** Единое правило блокирует документ, когда подозрительных фрагментов строго больше `suspicious_chunk_limit` (при значении 2 — с третьего). Имя `INJECTION_BLOCK_THRESHOLD=2` читается как «с двух», и до 03.10.2026 боевой поток блокировал именно с двух. Граница сдвинута на один фрагмент, чтобы у обоих потоков было одно правило в форме контракта каркаса. Последствие: документ с двумя инъекциями больше не блокируется целиком, из него исключаются два фрагмента. Сами подозрительные фрагменты исключаются всегда, порог на это не влияет.
- **Порог релевантности.** Сквозной сценарий (`retrieve_context_async`) отсекает векторные совпадения по `RELEVANCE_THRESHOLD` (0.40, см. [0004](0004-search-relevance-threshold.md)), как и боевой поток. Ослабление осталось только у самих функций `search_vector` и `search_hybrid`: их умолчание `threshold=0.0` — сигнатура контракта каркаса, тесты вызывают их напрямую на синтетических векторах, для которых порог был бы случайным. Кто вызывает эти функции мимо сквозного сценария, порог задаёт сам.
- **Жёсткие правила детектора.** До 07.10.2026 `guard_context` принимал фрагмент, если дешёвая модель сказала «чисто», даже с маркером вроде `SYSTEM:` или «игнорируй инструкции»; боевой поток такой фрагмент не открывал. Теперь оба потока устроены одинаково: жёсткие правила (`hard_rule_names`) перебивают вердикт «чисто». Вердикт «подозрительно» по-прежнему исключает фрагмент и без жёсткого правила; мягкое правило без жёсткого оставляет решение за моделью. Автопроверка Хекслета подменяет детектор; на тексте без жёстких маркеров поведение прежнее.
- **Хранилище.** Боевой поток читает и пишет `fragments`, слой совместимости работает с `chunks`. Они не пересекаются.

### Граница провайдера

Модель вызывается через `LlmClient`: синхронный `httpx.post` в OpenAI-совместимый `/chat/completions`. Пакет `openai-agents` стоит в зависимостях, но `Runner` из него не используется. Одноимённый `Runner` в `llm/client.py` — собственный класс, который запускает агента через тот же `LlmClient`.

Что это даёт:

- одна синхронная точка входа, одинаково пригодная для потоков активностей Temporal (`asyncio.to_thread`) и для тестов;
- таймаут, повтор (429, 5xx, обрыв), запись в `llm_calls` и выбор дешёвой модели (`cheap=True`) собраны в одном месте;
- строгий контракт: `response_format` со схемой Pydantic, затем разбор и точечный ремонт поля.

## Альтернативы

- **Удалить слой совместимости.** Чище, но автопроверка опирается на эти имена, и часть проверок перестанет проходить.
- **Перевести боевой поток на имена каркаса** (`chunks`, `run_agent`). Потеряем модель `fragments` с фильтрами по странице, разделу, артикулу и бренду и проверку ссылок по таблице `fragments`.
- **Вызывать модель через `Runner` из `openai-agents`.** Учёт стоимости и ретраи пришлось бы встраивать вокруг чужого вызова.

## Компромиссы

- Два слоя. Чтобы понять систему, нужно знать, какой настоящий. Для этого и нужна эта запись.
- Таблица `chunks` в боевом потоке не используется.
- Умолчания в `documents` (`0007`) нужны только вставкам в форме каркаса. Боевой код всегда пишет поля явно. Цена: у `filename`, `status`, `path` есть пустые умолчания, то есть схема мягче, чем нужна рабочему потоку. Миграция `0008` сужает эту мягкость: `CHECK (kind <> '' OR (filename <> '' AND status <> '' AND path <> ''))`. Строка без `kind` с пустым полем отвергается, пустое умолчание не попадёт в рабочие данные, если код забудет поле. Для строк с `kind` умолчания действуют как раньше. Ограничение создано `NOT VALID`: старые строки не проверяются, новые и изменяемые проверяются. Цена: вставка в форме каркаса без `kind` (`INSERT INTO documents (id)`) больше не проходит. `content_hash` остаётся `NOT NULL UNIQUE`, а умолчание у него случайное, поэтому две вставки без хеша не склеятся в один документ.
- Права. `with connection()` по умолчанию применяет миграции, но только недостающие: если все файлы уже записаны в `schema_migrations`, он делает чтение и берёт advisory-блокировку, права на DDL не нужны. Они требуются только на первом входе в пустую базу. Там, где роли приложения DDL не дают, ставят `AUTO_MIGRATE=false` и применяют схему заранее командой `python -m app.core.migrate`: соединение тогда ничего не создаёт, а при неприменённых миграциях останавливается с сообщением, какие именно и что выполнить. Умолчание `true` оставлено, потому что автопроверка открывает соединение на пустой базе и ждёт готовую схему. Боевой (асинхронный) путь миграций не применяет никогда.
- Слой совместимости тоньше, чем кажется по числу файлов: десять модулей контракта (`rag/*`, `guardrails/pii.py`, `guardrails/injection.py` и др.) — тонкие реэкспорты, настоящий код лежит в `services/`.
- База, созданная кодом до 03.10.2026, когда таблицы создавал сам `with connection()`, не содержит записей в `schema_migrations`. Миграция `0003` на такой базе остановится с «relation "documents" already exists». Такую базу пересоздают: `docker compose down -v`, затем `docker compose up -d --wait`. Подмена `CREATE TABLE` на `IF NOT EXISTS` сделала бы хуже: таблица осталась бы без `UNIQUE` на `content_hash`, который защищает загрузку от гонки двух одинаковых файлов.
- Каждый вход в `with connection()` делает проверку `schema_migrations` (один быстрый запрос под блокировкой). На пустой базе первый вход применяет все миграции.

Порядок запуска проверяет `tests/test_schema_order.py` на одноразовых базах: сначала соединение, потом миграции; сначала миграции, потом соединение; повторные входы; четыре параллельных первых входа.

## Когда пересмотреть

Если каркас изменится и автопроверка перестанет требовать эти имена, слой удаляется целиком вместе с `0006` и `0007`. Если боевой поток когда-нибудь перейдёт на `openai-agents`, граница провайдера переписывается заново.
