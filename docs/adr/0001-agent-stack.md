# 0001. Каркас агентного приложения

## Контекст

Дальнейшие задания курса строятся на одном репозитории. Каркас должен отвечать, где лежат конфигурация, HTTP, прикладные сценарии, оркестрация агента, хранение и тесты. Готовая платформа спрятала бы эти границы, а визуальный оркестратор сделал бы главным артефактом схему, а не код.

## Решение

- Слои: `app/routers` — HTTP, `app/services` — сценарии, `app/agents` — оркестрация, `app/repositories` — хранение, `app/schemas` — контракты, `app/llm` — граница провайдера, `app/core` — инфраструктура.
- База: образ `pgvector/pgvector:pg16`. `CREATE EXTENSION vector` только включает уже собранное расширение, обычный образ `postgres` для этого не подходит.
- Ресурс процесса: асинхронный движок SQLAlchemy и фабрика сессий. Они создаются в [lifespan](https://fastapi.tiangolo.com/advanced/events/) и освобождаются через `engine.dispose()`.
- Ресурс операции: сессия. Её выдаёт зависимость `get_db()` с `yield`. Одна сессия на всё приложение не используется: из нескольких параллельных задач это небезопасно.
- `pool()` отдаёт пул движка. `connection()` берёт одно соединение на операцию и возвращает его. Соединение не держат на всё время ожидания модели.
- Журнал структурный (`structlog`): уровень, `request_id`, операция, статус.
- Настройки — `pydantic-settings`. `DATABASE_URL` обязателен, без него приложение не стартует. Секреты в git не коммитятся, в репозитории лежит `.env.example`.

## Альтернативы

- Одна глобальная сессия на процесс.
- Образ `postgres:16` без собранного pgvector.
- Low-code оркестратор или платформа, где структура приложения скрыта.
- Alembic — отдельное решение, см. `0002-sql-migrations.md`.

## Компромиссы

Файлов больше, чем в одном `main.py`. Зато HTTP, сценарий, хранение и провайдер можно вызывать и тестировать по отдельности. Движок живёт всё время процесса, сессия — нет.

## Когда пересмотреть

Если хранение уйдёт с SQLAlchemy, если провайдера модели заменит другая граница, или если каркас переедет на платформу, где эти слои больше не наши.
