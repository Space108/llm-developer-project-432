# 0003. Повторы, поиск, цитаты, защита и учёт

## Контекст

К сдаче сервис ходит в модель, ищет по фрагментам, проверяет ссылки, считает стоимость и режет инъекции. Ниже — решения, которые спрашивают на защите.

## Решение

### Повтор вызова модели и повтор задачи

Вызов модели повторяем внутри `LlmClient` — таймаут, обрыв, 429, 5xx: это сеть и провайдер.  
Задачу / активность — в Temporal (`RetryPolicy`), когда упал шаг процесса целиком.

Граница: клиент не знает про `jobs`, процесс не крутит HTTP-повторы к модели. Иначе один контур начнёт заново гонять уже успешный шаг.

### Гибридный поиск и артикулы

Поиск по смыслу (`pgvector`) хорошо тянет характеристики («мощность блендера»), но короткие артикулы вроде `KTL-1700` в эмбеддинге часто слабы.  
Поиск по словам ловит точный токен.

Гибрид — слияние рангов (RRF): артикул поднимается за счёт словесного списка, характеристика — за счёт смыслового. Одна общая метрика на оба случая не нужна.

### PII до модели и фильтр на выходе

Маскирование (телефон, почта, ИНН, карта) — при сборке контекста, **до** промпта и **до** лога. Иначе контакты уже ушли в чужой API и в журнал.

Фильтр на выходе — второй рубеж: модель могла «вспомнить» контакт или частично выполнить инъекцию. Входные рубежи этого не видят.

### Проверка ссылок

Ссылка годится, только если фрагмент есть в базе **и** он был в поданном контексте.

Одного «есть в базе» мало: модель может сослаться на чужой чанк того же документа, которого ей не показывали — это всё ещё выдумывание.

### Низкая уверенность

В коде: `CONFIDENCE_THRESHOLD` (0.6) проверяют `run_context_pipeline` и `run_pipeline_sync`: выше порога вердикт «согласовано», ниже — «ожидание».  
В процессе: у `/generate-card` решение жёстче. Любая карточка доходит до статуса `ожидание` и ждёт сигнал, порог там не разделяет карточки. Человек смотрит карточку, `missing_fields` и источники, затем approve или reject. Порог под один плохой прогон не крутим.

### Рост стоимости карточки

Смотрим таблицу `llm_calls`: модель, токены, `cost`, `job_id`, `request_id`.  
И логи `llm_call` / `model_call` — какая роль звала модель (генерация, критика, детектор, судья).

Ищем: смену модели, лишние круги генерации/критики, лишние вызовы детектора, раздутый контекст.

### Состояние задачи в базе

API читает статус из `jobs`, не из Temporal UI. История движка — не единственный источник правды.

При рестарте воркера процесс продолжается с незавершённой активности; клиент видит актуальный статус в базе, а не «зависший» HTTP-ответ.

### Детектор инъекций недоступен

Правила помечают грубое; дешёвая модель уточняет помеченное.  
Если модель недоступна — фрагмент считаем подозрительным (fail-closed), в контекст не пускаем.

Грубые маркеры (`SYSTEM:`, «игнорируй инструкции») дверь не открывают, даже если слабая модель ответила «чисто». Иначе защита при своём отказе пропускает атаку.

## Альтернативы

- Один общий ретрай на весь workflow  
- Только смысловой поиск  
- Только фильтр на выходе для PII  
- Проверка «id есть в `fragments`»  
- Статус только в Temporal UI  

## Когда пересмотреть

Если провайдер даст идемпотентные вызовы с гарантией, эмбеддинги начнут стабильно ловить артикулы, или появится отдельный сервис модерации на входе документов.
